# 单机部署支持 300 人同时测评的容量评估

> 评估日期：2026-09-16  
> 场景：300 名独立评测者同时登录；00401 一期胜任力测评；每人 90 题、20 分钟；答题高峰不生成 PDF，报告在测评后错峰生成。

## 1. 结论

当前 Go 单机架构具备承载该场景的基础，但现有证据不足以直接承诺“300 并发已通过”。建议按以下规格部署，并在正式使用前完成一次 300 人全链路压测：

| 等级 | CPU | 内存 | 磁盘 | 服务端公网带宽 | 适用结论 |
|---|---:|---:|---:|---:|---|
| 最低试运行 | 4 vCPU | 8 GiB | 100 GiB SSD | 100 Mbps | 仅用于压测和低风险试运行；压测通过前不作为正式容量承诺 |
| 推荐正式配置 | 8 vCPU | 16 GiB | 200 GiB NVMe/高性能 SSD | 200 Mbps | 推荐用于 300 人同时登录、90题/20分钟、峰值不生成报告 |
| 带报告任务余量 | 16 vCPU | 32 GiB | 300 GiB NVMe | 300 Mbps | 可提高答题与后台任务隔离余量，但现有 LibreOffice 单槽设计仍应错峰排队，不能靠加硬件实现 300 份报告瞬时并发 |

推荐结论成立的前提：

1. 300 人使用独立身份、独立手机号或唯一人员记录，不能共用同一受测者账号。
2. Go、Nginx、MySQL、Redis部署在同一台服务器。
3. 测评高峰暂停 PDF 报告生成、批量下载、Excel 大导出和模板上传。
4. 使用 SSD/NVMe，磁盘长期保留至少 30% 空闲空间。
5. 上线前执行本文第 8 节的 300 人压测并达标。

## 2. 当前系统架构事实

当前单机链路为：

```text
浏览器 → Nginx → Go/Gin 单进程 :8092 → 同机 MySQL + 同机 Redis
                                      ├→ Chromium PDF 池（2路）
                                      └→ LibreOffice Word 转 PDF（单槽）
```

已核验配置：

- Go HTTP：读取超时 30 秒，写入超时 120 秒。
- MySQL连接池：最大连接 50，最大空闲 10，连接生命周期 1 小时。
- Redis：同机 6379/DB 1，客户端连接池使用库默认配置。
- Nginx：API代理连接超时30秒、发送60秒、读取120秒。
- systemd：单个Go进程，文件描述符上限65536。
- Chromium报告池：并发上限2。
- LibreOffice报告转换：全局单槽，同一时刻只处理1份。

因此，答题服务本身可以并发处理请求，但 MySQL 的50连接池会让大规模同步请求排队；PDF链则明确不适合在答题高峰并发运行。

## 3. 300人业务负载估算

### 3.1 请求量

每人正常流程：

- 登录/获取参与者令牌：1次；
- 创建或恢复试卷：1次；
- 获取90题试卷详情：1次；
- 每题选择后立即保存：90次；
- 交卷：1次。

核心答题保存总量：

$$
300 \times 90 = 27,000\text{ 次保存事务}
$$

20分钟均匀作答时平均保存速率：

$$
\frac{27,000}{20 \times 60}=22.5\text{ 次/秒}
$$

22.5 RPS 的平均值不高，风险来自三类同步突发：

1. 300人同时开始：短时间创建300份试卷和27,000条试卷题记录；
2. 大家按相似节奏作答：保存请求可能短时达到50～100 RPS；
3. 300人同时交卷：短时间读取27,000条答题明细并批量写入结果。

### 3.2 数据库工作量

每次答题保存是一个独立事务，包含：锁定本人试卷、校验题目归属、更新答案、统计已答数量、提交事务。不同评测者锁不同的试卷行，不存在全场共享行锁，但会竞争数据库连接、CPU和磁盘IO。

300人开考时大约新增：

- 300条试卷；
- 27,000条试卷题；
- 300次参与者状态更新。

300人交卷时大约新增：

- 3,000条二级维度结果；
- 600条一级维度结果；
- 300条效度结果；
- 300条总体结果；
- 600次试卷和参与者状态更新。

现有关键查询已具备 `paper_id`、`paper_id + answered`、发布快照和结果查询索引，主要容量风险不是全表扫描，而是集中事务对50连接池、MySQL日志刷盘和SSD延迟的压力。

## 4. 已有容量证据及边界

已有 staging 实测：

- 10并发创建100名参与者；
- 每份试卷384题，共写入38,400条试卷题；
- 100份题序均独立且刷新后稳定；
- 创建总耗时5.190秒；
- 单链创建耗时 p50=0.479秒、p95=0.758秒、最大0.837秒；
- 详情刷新 p50=0.063秒、p95=0.105秒、最大0.125秒。

这证明组卷和详情读取链有良好基础，但该测试没有覆盖：

- 300人并发登录和开始；
- 27,000次逐题保存；
- 300人集中交卷；
- 300份到期答卷由Worker兜底；
- 压测期间的CPU、内存、连接池等待和MySQL锁等待。

因此，当前结论是“技术上可行，需压测确认”，不是“已经验证支持300并发”。

## 5. 硬件需求详解

### 5.1 CPU

推荐8 vCPU。

- Go服务、Nginx和Redis本身CPU需求较低；
- MySQL会承担27,000个答题事务和集中交卷；
- JSON序列化、JWT校验和Go内存计分会占用一定CPU；
- 8核可以为Go、MySQL、操作系统和偶发后台任务保留隔离余量。

4 vCPU可用于压测或低风险试运行，但不应在没有300人实测的情况下直接作为正式配置。

### 5.2 内存

推荐16 GiB。

建议预算：

| 组件 | 建议预算 |
|---|---:|
| MySQL/InnoDB | 6～8 GiB |
| Go进程 | 1～2 GiB |
| Redis | 0.5～1 GiB |
| Nginx与操作系统 | 2～3 GiB |
| 文件缓存与峰值余量 | 3～5 GiB |

8 GiB主机可以运行当前系统，历史生产基线也验证过约7.5 GiB主机能运行现有服务，但这不能证明300人高峰有足够余量。16 GiB更适合正式场景。

### 5.3 磁盘

推荐200 GiB NVMe或高性能SSD：

- 随机写IOPS建议不低于3,000；
- 持续可用空间保持30%以上；
- 数据库、上传文件、报告、日志和备份必须分别设置保留策略；
- 禁止使用机械硬盘承载MySQL主数据；
- 测评前完成数据库备份，但备份任务不得与测评高峰同时运行。

单次300人、90题的数据增量本身不大，主要需求来自长期历史试卷、报告PDF和备份累积，而不是本次答题数据量。

## 6. 网络需求

### 6.1 服务端出口带宽

当前前端核心入口资源加答题页懒加载代码实测约：

- 未压缩：2,448,398 bytes/客户端；
- 已有预压缩副本：641,919 bytes/客户端。

300人同时冷启动，仅核心资源理论流量约为：

- 未压缩约735 MB；
- 预压缩约193 MB；
- 另需加字体、图片、登录页、题目详情和协议开销。

带宽建议：

| 服务端公网带宽 | 判断 |
|---:|---|
| 50 Mbps | 不建议；300人冷启动和资源重试容易形成明显排队 |
| 100 Mbps | 最低建议；必须确认Nginx实际启用gzip或gzip_static及浏览器缓存 |
| 200 Mbps | 推荐；可为300人集中打开页面留出更稳定余量 |
| 300 Mbps以上 | 适合还有其他业务流量或不能提前预热页面的场景 |

答题稳定阶段主要是小JSON请求，平均22.5次保存/秒，带宽占用很低；网络峰值主要发生在页面首次加载和断网后的集中刷新。

### 6.2 网络质量

客户端到服务器建议满足：

- 往返延迟：最好低于100ms；
- 丢包率：低于1%；
- 抖动：低于30ms；
- DNS稳定并至少提前一天完成解析；
- 服务器、MySQL和客户端设备均启用可靠NTP时间同步。

如果300人在同一现场使用Wi-Fi：

- 使用企业级Wi-Fi 6/6E；
- 按每个AP稳定承载30～50个活跃终端规划，建议6～10个AP；
- AP使用有线千兆回程，禁止无线级联；
- 出口建议至少300 Mbps，下行和上行均不能被其他下载、视频或云盘任务占满；
- 正式测评前使用300台或等效终端做现场漫游、DNS、丢包和断网恢复演练。

### 6.3 端口与安全边界

- 对评测者仅开放HTTPS 443；HTTP 80只做跳转；
- 不向公网开放Go 8092、MySQL 3306和Redis 6379；
- SSH 22仅允许管理员固定IP或VPN；
- 配置正式域名和可信TLS证书；
- 如部署在内网，评测终端必须能稳定访问该域名及证书链，不依赖临时IP和自签名证书。

## 7. 单机部署的可用性边界

单机意味着以下任一故障都会影响全部300人：

- 主机硬件故障；
- 系统重启；
- MySQL故障或磁盘满；
- Nginx或Go进程异常；
- 单线路网络中断。

当前Go服务可自动重启，答题每题即时落库且支持断点恢复，能降低浏览器刷新造成的数据损失；但这不等于高可用。关键正式测评建议至少具备：

- 云盘快照或异机数据库备份；
- 监控告警；
- UPS或云主机基础设施保障；
- 双线路或可切换网络；
- 测评前冻结版本和配置；
- 故障处理联系人及恢复预案。

若客户要求“单机故障也不能中断”，则单机方案不满足需求，必须升级为应用多实例、独立数据库和负载均衡架构。

## 8. 上线前300人压测门禁

建议按真实节奏执行以下四阶段：

1. 300个独立身份在60秒内完成登录；
2. 300人在30秒内开始测评并读取90题；
3. 20分钟内完成27,000次保存，加入50～100 RPS短时同步波峰和5%重试；
4. 300人在10～30秒内集中交卷；另做一次300人全部离线、由到期Worker兜底的故障场景。

建议验收指标：

| 指标 | 建议门槛 |
|---|---:|
| 全链路业务成功率 | ≥99.9%，且答卷/答案/结果零丢失 |
| 单题保存 p95 / p99 | ≤1秒 / ≤2秒 |
| 开始与详情 p95 | ≤2秒 |
| 集中交卷 p95 / p99 | ≤3秒 / ≤5秒 |
| HTTP 5xx | 0 |
| Go进程峰值CPU | <85% |
| 主机持续CPU | <70% |
| 内存使用 | <80%，无swap抖动/OOM |
| MySQL行锁死锁 | 0 |
| 数据库连接等待 | 无持续增长，压测结束后快速归零 |
| Worker兜底 | 300份最终全部完成，无重复结果 |

压测必须同步记录Go CPU/RSS/goroutine、数据库连接池等待、MySQL Threads_running/慢查询/行锁等待、Redis延迟、磁盘IO等待、Nginx upstream响应时间和4xx/5xx。

## 9. 运行安排建议

1. 提前导入并校验300名评测者，确保身份唯一。
2. 提前5～10分钟让评测者打开入口，使静态资源和DNS缓存预热。
3. 开始和交卷提示可按30～60秒自然错峰，降低同步尖峰。
4. 测评窗口内禁用报告生成、批量下载、导出、备份和系统升级。
5. 交卷后先核对300份结果完整性，再按队列错峰生成报告。
6. 现有LibreOffice单槽生成300份报告可能需要较长时间，应按批次执行并单独监控，不能纳入答题实时SLA。

## 10. 最终建议

对于“300名独立评测者同时登录、90题、20分钟、峰值不生成报告”的场景，建议采购或配置：

- **8 vCPU / 16 GiB RAM / 200 GiB NVMe SSD**；
- **200 Mbps服务端公网带宽**；
- 如同一现场无线接入，采用**千兆有线出口 + 6～10个企业级Wi-Fi 6 AP**；
- 正式上线前必须通过300人真实节奏压测。

若预算受限，可以从4 vCPU / 8 GiB / 100 Mbps开始做压测，但只有在压测门禁全部通过后才能用于正式测评。若要求同时立即生成300份PDF或要求单机故障无感，则应改用报告异步工作节点或高可用架构，而不是继续提高单机参数。

## 11. 云服务器采购规格

向云厂商采购时，不只看“8核16G”，应按下面的完整规格询价和验收。

### 11.1 推荐生产规格

| 云资源 | 推荐要求 | 说明 |
|---|---|---|
| 实例类型 | 通用型或计算型，8 vCPU / 16 GiB | 不选突发性能、共享核或长期积分型实例，避免测评高峰被CPU积分限速 |
| CPU架构 | x86_64 | 与当前Linux二进制、Chrome、LibreOffice兼容路径一致 |
| 系统盘 | 60～80 GiB SSD | Linux、Nginx、Go、MySQL、Redis及系统日志 |
| 数据盘 | 200 GiB高性能云盘/NVMe SSD | MySQL数据、上传文件、报告和运行目录；基线至少3,000 IOPS、吞吐至少125 MB/s |
| 公网IP | 1个固定公网IPv4或EIP | DNS必须绑定固定地址，禁止每次开关机改变公网地址 |
| 公网带宽 | 200 Mbps独享或有明确保障的固定带宽 | 不采用标称峰值高但无保障的廉价共享带宽作为正式测评入口 |
| 流量包 | 至少1 TiB/月起步 | 实际按访问次数、报告下载量和云厂商计费方式复核 |
| 操作系统 | Ubuntu 22.04/24.04 LTS或同等级稳定Linux | 需确认MySQL、Redis、Nginx、Chrome和LibreOffice可安装 |
| 快照 | 每日自动快照，保留7～14天 | 快照不能替代数据库逻辑备份 |
| 异机备份 | 每日MySQL备份到对象存储，保留至少30天 | 备份必须位于不同故障域，定期执行恢复演练 |
| 监控 | CPU、内存、磁盘、IOPS、带宽、TCP连接、进程和HTTP探测 | 测评期间必须有人观察告警 |

推荐数据盘单独挂载，避免系统日志、数据库和报告同时写满根分区。数据库和备份目录应设置容量告警：使用率70%预警、80%严重告警。

### 11.2 网络采购方式

云厂商常见公网产品有“固定带宽”和“按流量/共享带宽”两种。正式测评建议：

1. 选择固定公网IP/EIP；
2. 选择200 Mbps固定带宽，或能够明确保证200 Mbps可用吞吐的共享带宽产品；
3. 如果只能购买100 Mbps，应提前5～10分钟让300人打开页面并确认Nginx压缩、缓存生效；
4. 不要把云厂商实例网卡标称的内网Gbps能力当作公网带宽；
5. 确认带宽是上下行分别限速还是按出方向限速，页面加载主要消耗服务器出方向带宽；
6. 对象存储、快照和备份流量不能在测评窗口抢占公网出口。

如使用CDN承载前端静态资源，可显著降低源站冷启动流量。此时可采用：

- CDN：缓存带哈希文件名的JS/CSS/字体/图片；
- 源站公网带宽：最低50～100 Mbps，推荐100 Mbps；
- API、登录和答题请求仍回源，不得缓存；
- 发布后先完成CDN预热和版本一致性检查。

未使用CDN时继续按200 Mbps源站带宽采购，不建议为了节省带宽直接降至20～50 Mbps。

### 11.3 区域和线路

- 云区域应选择靠近大多数评测者的区域；同一城市或同一区域优先。
- 评测者跨运营商时，应选择BGP多线公网，不使用单运营商廉价线路。
- 若客户主要位于中国大陆并通过公网域名访问，应提前确认域名备案、云平台接入备案和HTTPS证书要求；这些流程不能等到测评当天处理。
- 若客户从企业内网访问，应提前确认代理、防火墙、DNS和HTTPS解密设备不会拦截登录及答题请求。
- 测评前从客户真实网络执行延迟、丢包、DNS解析、页面冷启动和连续答题测试，不能只在云服务器本机测试。

### 11.4 安全组与端口

| 端口 | 来源 | 是否开放 | 用途 |
|---:|---|---|---|
| 443/TCP | 评测者网络或公网 | 是 | 正式HTTPS入口 |
| 80/TCP | 公网 | 可选 | 仅跳转HTTPS |
| 22/TCP | 固定管理员IP/VPN | 是，严格限源 | 运维SSH |
| 8092/TCP | 公网 | 否 | Go后端，仅本机Nginx访问 |
| 3306/TCP | 公网 | 否 | MySQL，仅本机访问 |
| 6379/TCP | 公网 | 否 | Redis，仅本机访问 |

建议同时启用云防火墙或基础DDoS防护、登录失败告警、SSH密钥登录、禁用密码直登，并配置TLS 1.2以上的可信证书。

### 11.5 可选高可用升级

如果客户不能接受单台云服务器故障导致300人中断，采购方案应升级为：

```text
公网负载均衡
    → 2台应用服务器（每台4～8 vCPU、8～16 GiB）
    → 云数据库MySQL高可用版
    → 云Redis主从/高可用版
    → 对象存储保存报告
```

当前报告生成和部分进程内锁按单实例设计；升级多应用实例前必须完成共享文件、分布式互斥、会话和报告任务队列改造，不能直接复制两台当前服务器就视为高可用。

### 11.6 云资源验收清单

正式压测前确认：

- 实例不是突发性能型，8核在持续压力下不会降频；
