# 2026-10-09 开发与发布会话效率复盘

## 结论

本次功能本身范围明确，但耗时主要不在编码，而在**环境事实发现过晚、验收脚本环境耦合、失败信息不足、发布包反复重封存**。安全门禁和真实验证不能删除；应把它们前置、模板化并一次性执行。

## 本次主要耗时点

1. **production事实晚发现**：MySQL 5.7排序规则、nginx实际监听8090、旧48维唯一name/order约束均在执行后才暴露。
2. **staging脚本不能直接复用**：配置段名、Redis认证、Python 3.8语法、硬编码staging地址/清理器导致重复改写。
3. **错误收据过度脱敏**：只返回异常类型，不返回阶段、路由和受控错误消息，造成盲目复跑。
4. **把结构发布误当业务可运行**：production已装00401结构，但未装固定10维/90题；首次完整E2E才发现。
5. **测试假设偏离真实Schema**：005清理器不接受合法下划线ID；00401导出依赖可选XML range；报告门禁错误文案被假定完全一致。
6. **发布单位过大**：一次会话同时包含代码、数据、模板、前端、多个产品验收，导致每个小修都重新评估全链。
7. **重复读取和重复全量验证**：相同状态被多次查询；聚焦测试、全量测试、构建和远端验收没有稳定的阶段边界。
8. **历史文档体量大**：大量旧PARTIAL/BLOCKED信息增加定位成本，虽已建立project-status入口，但执行中仍多次回查历史。

## 强制效率策略

### 1. 先做一张“环境差异表”

在任何部署脚本编写前，一次性只读采集：OS/运行时、DB版本和collation、服务管理器、监听端口、配置key、Schema签名、目标内容计数、现有唯一约束。staging与production并排输出；后续不再猜测。

### 2. 小变更采用四阶段固定流水线

1. **Scope**：只列本次文件、接口、表和验收链。
2. **Local**：RED→GREEN、聚焦测试；完成后只跑一次全量和一次build。
3. **Preflight**：候选包在目标环境执行零写只读合同；所有会导致写后失败的断言必须在这里完成。
4. **Deploy+Accept**：单次备份、单次切换、单次E2E、单次回写。

同层失败最多修正两轮；第三轮必须停止并重新审查假设，禁止不断微调远端脚本。

### 3. 验收脚本必须环境无关

- 由`APP_ENV`和配置读取端口/DSN/Redis/JWT，不写死local/staging地址。
- 兼容目标机实际Python版本；禁止使用未在目标机验证的语法。
- stdout只输出一条非秘密JSON收据；收据包含`failedStage`、route、受控msg、cleanup结果。
- 测试资源统一使用唯一marker，并把所有权闭包和FK顺序封装成共享cleanup库。
- “正式能力未批准”必须作为可声明的预期分支，而不是写死同一句错误文案。

### 4. 发布标记驱动增量包

以[release-markers.md](release-markers.md)为唯一环境版本索引。每次候选只计算当前标记到目标标记的文件、Schema、内容和资产差异；不要重新扫描/提交整个历史工作树。

### 5. 数据和代码分开批准

代码可运行不等于业务内容已批准。发布清单分别标识：

- runtime/schema
- source content
- formal report content/template
- synthetic TEST baseline

缺哪一层就明确fail-closed，不到E2E时才发现。

### 6. 一次性并行只读，串行写入

文件搜索、调用点、Schema/配置/端口盘点可并行；所有生产写操作严格串行。这样保留安全性，同时减少主会话中的重复工具往返。

### 7. 复用既有成功收据

未涉及的产品只做最小只读冒烟；只有公共代码、Schema或共享基础设施发生变化时才重跑完整链。不要因005单点修复默认重跑所有00401/MBTI写链。

## 目标指标

- 明确的小型代码修复：1次RED、1次GREEN、1次全量、1次build。
- 单环境发布：1次preflight、1次备份、1次部署、1次E2E。
- 远端失败：收据必须在第一次就定位到阶段和断言。
- 发布后：5分钟内完成release marker和project-status回写。
